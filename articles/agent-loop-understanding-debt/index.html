2026.11.15 AI 与软件工程

下｜AI 越能自己进化，团队越不能放弃理解

当 Agent 不只改答案，还开始改“寻找答案的方法”，我们面对的就不再是一个更勤快的助手，而是一套会改变自身工作机制的系统。

前两篇我们讲了两个层次：第一层，是从单次提示词走向目标循环；第二层，是给循环补上验证器、状态和停止条件。

接下来这个问题更有意思，也更危险：如果 Agent 可以观察自己的运行轨迹，发现当前搜索方式效率不高，然后修改下一轮的搜索机制，会发生什么？

这就是 《Bilevel Autoresearch》预印本 讨论的“双层循环”。很多人看到这里，会立刻用上“自我进化”四个字。这个说法很有传播力，但我更愿意把它收窄一点：它不是神秘的自主意识，而是机制级的迭代。

只有把这个边界说清楚，我们才不会一边神化它，一边低估它带来的治理难题。

内层改结果，外层改搜索方法

普通循环做的事情，是围绕一个目标不断尝试。

它提出改动，运行实验，读取指标，然后决定保留或回滚。这里被优化的是任务结果，比如更低的验证损失、更高的测试通过率、更少的错误。

双层循环在外面又加了一层。外层不直接解决同一个任务，而是读取内层循环的代码和轨迹，判断它为什么卡住、为什么总在重复某类尝试、哪些方向因为模型的先验偏好而一直没有被探索。然后，外层生成新的搜索机制，注入内层，再观察结果。

论文的摘要把分工说得很准确：

“The inner loop optimizes task performance; the outer loop optimizes how the inner loop searches.”

内层优化任务表现，外层优化内层如何搜索。

这两层使用的是同一个 LLM。也就是说，结果改善不一定来自“换了一个更聪明的模型”，而可能来自系统结构发生了变化。

— 双层循环：内层优化结果，外层优化搜索机制，人负责目标与理解

“5 倍提升”到底意味着什么

0xCodila 的文章标题提到“5 倍”。这个数字指论文中单项实验的指标改善幅度。

在 Karpathy 的 GPT 预训练基准上，论文报告外层循环带来的改善为 -0.045 val_bpb，单独运行标准内层循环为 -0.009 val_bpb。两组的改善幅度分别是 0.045 和 0.009，每字节比特数越低越好，前者是后者的 5 倍。

这个实验提示，同一个模型，在不同的搜索架构下，可能表现出明显不同的改进能力。

但它没有证明“给任何业务 Agent 套两层循环，都能获得 5 倍生产力”。外层循环还消耗了额外的推理预算和运行时间，实验发生在明确的训练基准和单一指标里。换到需求分析、内容创作、客户服务或企业决策，反馈信号和风险结构完全不同。

我对这类数字一直有个原则：可以被它启发，但不要被它代替判断。先问清实验对象、指标、预算和对照组，再决定它对自己的业务到底意味着什么。

架构为什么能够放大同一个模型

这件事对架构师很有启发。

我们常常把 AI 能力看成模型参数：更大的模型、更长的上下文、更高的基准分数。但在真实系统里，模型只是一个部件。它周围的记忆结构、工具接口、验证器、任务分解、角色分工和反馈节奏，会显著改变最终表现。

同一个模型，如果每轮都从头猜，和能够读取失败轨迹、主动改变搜索策略，当然不是同一种系统。

这与传统软件架构其实很像。数据库没有变，但索引和查询计划变了，系统表现会变；成员能力没有变，但反馈周期和责任边界变了，团队表现也会变。能力不只存在于组件里，也存在于组件之间的组织方式里。

所以，Agent 时代一个重要的设计对象，会从“给模型什么提示词”升级成“系统如何产生、验证和修正自己的行动策略”。

可一旦系统能够修改机制，风险也会同步升级。

最容易被忽略的，是理解债务

0xCodila 在 《Loop Engineering》 里提到一个我很认同的概念：comprehension debt，理解债务。

技术团队对技术债并不陌生。为了赶进度先写下的临时代码，未来要连本带息地维护。理解债务也类似：系统交付得越来越快，但团队对它为什么有效、边界在哪里、失败时会发生什么，理解得越来越慢。

最开始，这种差距看起来没有问题。测试通过了，指标也变好了，为什么还要花时间看过程？

可一旦环境变化、指标失真、依赖升级或出现边缘故障，团队才会发现：成品是自己的，因果链却不是。没人知道哪个机制不可替换，也没人知道一次看似普通的修改会破坏哪条隐含假设。

这笔债还有一个麻烦：它在系统表现良好时最容易被忽略。Agent 越能快速交付，人越容易放弃追问；人越不追问，下一次就越依赖 Agent。速度和不理解互相强化，最终形成一个很难退出的循环。

比理解债务更危险的，是认知投降

理解债务至少还意味着“以后补”。认知投降则更彻底：我们不再准备形成自己的判断，只希望系统给一个看起来合理的答案。

它有几个很典型的信号。

  • 只看最终结果，不看证据链；

  • 只问“能不能做”，不问“为什么这样做”；

  • 指标上涨就接受，不检查指标是否仍代表真实目标；

  • Agent 给出三个方案，人只负责挑一个顺眼的；

  • 出现异常时，第一反应是再问一次 AI，而不是建立自己的故障模型。

说实话，这种状态很舒服。判断是一件消耗认知的工作，把它交出去，人会立刻感觉轻松。

但架构决策、业务取舍和风险承担从来不是一道有标准答案的选择题。真正重要的信息，往往没有完整地写在上下文里；真正昂贵的错误，也常常来自目标定义错了，而不是执行不够快。

我的态度很明确：可以把搜索交给 Agent，把重复实验交给 Agent，把证据整理交给 Agent，但不能把“我们为什么相信这个结果”一起交出去。

人的工作不是消失，而是上移

当循环越来越强，人确实不需要再盯着每一步操作。可人的职责不会因此消失，它会向上移动。

第一，定义值得优化的目标。系统可以极快地追一个指标，人必须确保这个指标没有把真实价值压扁。

第二，设计验证器。决定哪些证据足够、哪些异常必须阻断、什么时候需要多种信号交叉确认。

第三，规定权力边界。Agent 可以读什么、改什么、花多少钱、联系谁，哪些动作不可逆，哪些必须先获得批准。

第四，维护因果理解。不是要求每个人阅读每一行轨迹，而是要保留足够的模型：关键机制为何存在、改动如何影响结果、故障时从哪里开始排查。

第五，承担最终责任。系统可以给建议，可以执行动作，但谁决定把结果带进真实世界，谁就不能只做一个没有观点的确认按钮。

这也是我理解的“人在回路中”。它不是每一步都手动点确认，也不是在流程图最后画一个小人。人的位置应该放在目标、边界、例外和责任上，而不是放在机械接力上。

给团队一条“不放弃理解”的底线

如果团队准备引入更强的 Agent Loop，我建议同时建立四条底线。

任何自动结论，都能追到证据

不仅保存最终答案，还要保存关键输入、工具结果、验证信号和接受理由。审计不是为了追责，而是为了让学习可以发生。

任何关键机制，都有人能够解释

不要求全员掌握，但至少有明确的责任人能解释目标、验证器、权限和失败模式。不能让一个长期运行的关键循环成为组织里的黑箱孤儿。

任何指标，都有对应的反指标

追求速度，就同时观察错误率；追求转化，就同时观察投诉和留存；追求自动修复率，就同时观察回滚率和重复故障。一个指标负责踩油门，另一个指标负责提醒你别冲出道路。

任何自主性，都配有退出机制

暂停、回滚、降级到只读、切换人工流程，这些能力必须在系统正常时就准备好。事故发生后才讨论怎么停，通常已经晚了。

结语：让 AI 多做事，让人多理解

Loop Engineering 真正有价值的地方，不是让我们少写几条提示词，而是迫使我们重新思考：一项工作是怎样被定义、执行、验证、记忆和治理的。

当 Agent 能够连续行动，我们要把验证器设计得更可靠；当它能修改搜索机制，我们要把理解与责任放得更高。

未来强大的团队，未必是人亲手完成每一步的团队，也不会是把一切都交给 AI 的团队。它更像一种新的分工：机器负责扩大搜索和执行，人负责守住目标、因果、边界和价值判断。

AI 越能自己进化，团队越不能放弃理解。

这不是对技术的保守，而是让技术真正可持续的前提。
