自动化跑通一次以后，还要补哪些检查

手动点一次，结果成功了。第二天定时运行，输入还没到；第三天又重复触发，生成两份同名报告。自动化的难处，常在这些第一次演示没有遇到的情况里。

先把输入就绪、重复执行、失败处理和停用办法写清，再让任务按时间运行。定时器只负责触发，可靠交付还需要自己的规则与检查。

先让手动流程稳定下来

准备input/tasks.csv，包含任务、负责人、截止、状态与来源。日期在这组材料中只作教学字段，不代表正在跟踪的实际项目。

先手动读取、生成简报、核对来源。缺少T02截止时间应列为待确认，不自动安排一个日期，更不因为“待确认”就直接判断逾期。

这一步还没稳定，就不要把错误每天重复执行。先检查实际产物、字段口径与文件保存位置，再讨论调度。

为本次运行定义批次与状态

同一批材料应该能被识别。可以使用项目标识、业务日期和输入版本组成batch_id，输入内容更新时形成新版本。

状态可以区分pending、running、completed、failed；只有文件保存与核对完成以后，才写completed。模型回复“完成”不是状态转换的唯一依据。

同一批次再次到来，先检查已有完成记录和产物是否一致。多任务并发时，仅先读JSON再写JSON并不能保证防重，需要锁或原子登记，不能靠一句“不要重复”假装解决。

设置调度时确认运行环境

在当前客户端的定时任务入口设置任务名称、提示词和执行时间，核对运行环境能否取得输入、使用所需能力、保存输出。

电脑需要保持什么状态、使用本地还是云端任务、哪些Skill在该环境可用，都要按当前产品说明和实际测试确认。不要因为手动客户端有某项能力，就推断定时任务环境也相同。

先用短时间间隔做一次可观察测试，确认后再改成正式周期。教程示例不要求读者直接启用长时间无人值守任务。

故意制造四种失败

第一，空表。只有表头没有任务时，按业务要求说明无输入或无事项，不能凭空写一份风险报告。

第二，缺字段。删除status列，预期指出字段缺失并停在执行前，不将所有任务默认视为进行中。

第三，重复触发。同一batch_id运行两次，预期只有一个有效结果；已经失败或输出损坏时，则根据恢复规则处理，不盲目跳过。

第四，保存失败。将输出指向一个没有写入权限的教学位置，预期说明没有完成文件交付，保留已有中间结果，不把文件名写进报告就称为保存成功。

失败演练应该在副本中进行，不能为了测试自动化故意破坏正式资料。

重试要区分网络与确定性错误

短暂超时可以设置有限次数与间隔，并记录次数。认证失败、权限拒绝、字段缺失属于不同问题，反复调用不会自动修好。

外部写入更要谨慎：请求超时可能是“已经成功但没收到回执”。先查状态或已有对象，再决定重试，避免重复任务、重复消息或重复草稿。

这些限制需要由调度、脚本或工具实现并验证，不是写进提示词就天然成立。模型替换也要重新核对输出，不能把任何替代模型都视为效果相同。

留下停用和恢复的入口

记录任务名称、触发周期、运行位置、日志与状态路径、最后成功批次和停用步骤。停用调度不会自动删除已有成果，恢复时先检查输入与状态一致。

先自动生成简报，再考虑发通知；先验证只读与本地保存，再考虑写业务系统。每次扩展都明确操作对象与回读方法。

自动化真正省下的是重复执行已明确的方法。把异常、重复与恢复也设计进去，WorkBuddy才能在条件不合适时停下来，并留下下一步能处理的证据。
