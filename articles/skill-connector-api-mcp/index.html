Skill、连接器、API 和 MCP 怎么分工？

一个任务既要查数据，又要整理报告，常会同时出现Skill、连接器、API和MCP几个词。名字放在一起，很容易以为装一个Skill就能访问企业系统。

我会先把方法和数据入口分开，再确认登录身份与业务权限。知道报表怎样做，不代表已经有权读取报表的数据。

先说清要读什么，暂时不写入

本次目标：查询一个已获授权的教学项目说明，提取项目状态与来源。只读这份文档，不创建任务、不改业务数据、不发送消息。

在正式系统里，把“教学项目说明”换成具体文档或资源标识，并核对账号是否可见。不要先配一个访问范围很大的账号，等任务结束再讨论权限。

用户登录、接口可调用、本人有权读取指定资源，是三个需要分别确认的条件。

Skill说明做法，连接器提供入口

Skill可以约定“读资料→提取→生成简报→核对”的流程。API是系统对外提供的调用接口。MCP 可以让宿主以标准方式发现并调用工具。WorkBuddy 连接器则将具体服务的连接和授权放到产品入口中。

这里说的是职责，不是要求每次都自己开发MCP服务器。若当前官方连接器已经支持目标服务，先阅读说明，用最小只读测试确认。

一个整理方法再完善，也不会自然获得账号权限。反过来，接口能返回很多记录，也不意味着当前任务需要全部读取。

登录与授权按当前服务方式完成

在客户端连接器入口选择已确认服务，按它支持的授权流程完成登录。需要人工浏览器登录时由本人操作，不把密码、票据或静态token写进文章、项目规则或共享文件。

演练失效与拒绝，再考虑扩展

至少检查正常只读、登录失效、资源无权限三种结果。正常场景交产物；失效场景说明需要重新登录；无权限场景明确拒绝，不尝试借用他人凭据。

以后增加写入、通知或自动化，需要重新确认操作对象、权限和回读方法。当前只读成功，只能证明这条读取链路在本次条件下可用。

企业接数据的第一步，不是堆叠更多工具。先把方法、入口、身份和权限分清，用一个授权资源走通读取与核对，再谈更长的工作流。
