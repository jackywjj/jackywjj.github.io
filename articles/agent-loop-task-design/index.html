2026.11.13 AI 与软件工程

上｜你以为在用 Agent，其实自己才是那个工作流

我们以为自己已经进入了 Agent 时代，实际做的却可能还是“人工接力”：人来拆任务，人来复制结果，人来发现错误，人来提醒 AI 继续。工具换了，工作流并没有换。

这段时间，越来越多人开始说自己在“用 Agent”。但我认真看了一圈，发现里面有个挺有意思的错位：不少人只是把原来的搜索框换成了聊天窗口，把一条提示词换成了十条提示词，然后把每一步之间的衔接工作，继续留给自己。

先让 AI 写一个方案，我读完再让它补数据；数据不对，我告诉它重查；代码跑不起来，我把报错贴回去；它说完成了，我再打开文件检查。整个过程看起来很智能，真正负责计划、调度、验收和重试的，还是屏幕前的那个人。

借用 0xCodila 的比喻，AI 是扳手，你才是那台发动机。

0xCodila 在 《Loop Engineering》 里用一段话解释了这个差别。

“A prompt is one instruction. A loop is a goal the AI pursues until it is achieved.”

提示词是一条指令；循环则是一个目标，以及围绕这个目标持续行动、检查和修正的机制。

这不是换一个更时髦的名词，而是工作方式真的变了。

提示词解决一次回答，循环负责一个结果

提示词思维关注的是：我下一句话该怎么说，才能让 AI 回答得更好？

循环思维关注的则是：我要怎样设计一个系统，让 AI 知道目标、能够行动、看得见结果，还能在失败之后调整？

前者优化的是单次交互，后者设计的是一段运行过程。

比如，让 AI “检查这段代码有没有问题”，这是一条提示词。它可能给出很专业的解释，也可能一本正经地漏掉真正的 bug。

如果改成一个循环，事情会变成这样：先读取需求和代码，再运行测试；如果测试失败，就定位失败用例并修改；修改后重新测试；全部通过后，再运行构建和静态检查；任何一步超过重试上限，就停止并把证据交给人。

这里真正重要的，不是 AI 多说了几轮，而是系统出现了四个结构：目标、动作、反馈和决策。

没有这四个结构，再长的对话也只是人工遥控。每一步仍然等着你按一下“继续”，那不叫自主工作流，只能叫高级一点的复制粘贴。

— 从人工接力到目标闭环：Prompt 与 Loop 的差别

站在架构师视角，Loop 本质上是一种控制系统

我更愿意用架构语言理解这件事：Agent Loop 不是一个“更聪明的机器人”，而是一个带反馈的控制系统。

输入侧有目标、上下文和约束；执行侧有模型与工具；反馈侧有测试、指标或规则；决策侧负责判断继续、回滚、换方案还是交给人。只要其中一环缺失，闭环就会退化。

最常见的退化有三种。

第一种，**只有目标，没有验证。**你告诉 Agent “把页面优化好”，它改了一轮，然后宣布完成。问题是，“好”到底是什么？页面能构建就算好，还是加载时间下降、可访问性通过、关键流程没有回归才算好？目标不能被验证，Agent 只会学会用语言说服你。

第二种，**只有动作，没有状态。**每一轮都像失忆一样重新开始，不知道试过什么、失败在哪、哪些结论已经确认。循环看起来转了很多圈，实际可能一直在原地打滑。

第三种，**只有继续，没有停止。**模型不断尝试，成本继续累积，改动范围越来越大，最后为了修一个小问题，顺手重写了半个项目。没有停止条件的自主性，不是能力，是风险。

所以，判断一个 Agent 是否真的“在工作”，别只看它能不能调用工具。要看它是否拥有一条可审计的闭环：做了什么、看到了什么、为何继续、为何停止。

不是所有任务都值得做成 Loop

Agent Loop 最近很热，很容易让人产生一种冲动：凡事都自动化，最好晚上交代一句，第二天早上直接收结果。

我对此反而比较克制。循环不是越多越好，而是要放在反馈清楚、重复足够、风险可控的地方。

我会先问四个问题。

这个任务会不会重复？

如果一年只做一次，而且每次条件都完全不同，搭循环的成本可能比手工完成更高。真正值得投入的，通常是每周甚至每天重复出现的工作。

结果能不能自动判断？

测试是否通过、页面能否构建、接口响应是否符合约定、数据是否落在阈值内，这些适合闭环。至于“这篇文章是否真正打动人”“这个战略判断是否值得下注”，AI 可以辅助，但很难独立担任最终裁判。

失败的代价有多大？

在隔离分支里改代码，失败了可以回滚；直接给客户发邮件、修改生产数据、支付费用，失败就不是多跑一轮那么简单。动作越难撤销，权限越要收紧。

重试预算是否划算？

循环靠多次尝试换取更好的结果，也会消耗更多推理、时间和外部资源。便宜的小实验可以多试，昂贵的调用必须有上限。不要为了省十分钟人工，烧掉一晚上额度。

如果这四个问题里有两三个答不上来，我不会急着上完整 Loop。先用一个明确的检查清单，加一次人工确认，往往更可靠。

真正要升级的，不是 Prompt，而是任务设计能力

过去大家研究提示词，重点是如何把要求说清楚。到了 Agent 阶段，这当然仍然重要，但已经不够了。

你还要定义工作范围：哪些文件能改，哪些不能碰；要给出完成标准：什么证据可以证明做完；要安排失败路径：第一次不行怎么办，连续三次不行又怎么办；还要留下升级出口：什么时候必须停下来找人。

这几件事听上去不炫，甚至有点像传统的软件工程。可真正可靠的 Agent 系统，最后拼的恰恰就是这些基本功。

很多人希望找到一条“万能 Prompt”，最好一句话就让 AI 把复杂任务做完。我的判断是，未来更值钱的能力不是把一句话写得越来越长，而是把模糊愿望变成可执行、可验证、可停止的系统。

这也是为什么我把它叫作 Loop Engineering，而不是 Prompt Engineering 2.0。提示词是循环中的一个部件，工程才是把所有部件组织起来的那件事。

先做一个最小闭环，而不是搭一座自动化大厦

如果你想试，我建议从一个低风险任务开始。不要先装一堆工具，也别急着安排十个子 Agent。

只写清楚六行：

protocol.txt

然后让它只跑三轮。你观察的重点也不是“AI 看起来忙不忙”，而是每一轮有没有基于上一轮证据做出不同决策。

如果没有，问题大概率不在模型，而在你的循环设计里：验证器太模糊、状态没有留下、工具给得不对，或者目标本身根本无法被机器判定。

我认为，这才是 Agent 时代最值得练的第一项能力：别再只做那个不停提醒 AI 下一步的人。把你脑子里的任务流程，第一次认真地画出来。
